## 1. 개요/목표

- my-todoList는 인증된 사용자가 카테고리 기반으로 할일(시작일/종료일 포함)을 관리하는 웹 서비스다.
- 배경 및 도메인 규칙은 `1-domain-definition.md`(v0.2)를 따른다.
- 비즈니스 목표: 서비스 동시 접속 1,000명 처리 가능한 구조로 설계·구현한다.
- 개발 제약: 1인 개발, 2일 내 핵심 기능(MVP) 완성.

## 2. 목표 사용자

- 학생, 20대~50대 직장인. 개인 일정/할일을 카테고리별로 정리하고 진행 상태를 추적하려는 사용자.
- 상세 페르소나 시나리오는 본 문서 범위 밖(생략).

## 3. 범위

### 3.1 MVP 범위 (2일 내 완성, 1인 개발 기준)

**Must (필수)**
- 회원가입/로그인 (UC-01, UC-02, BR-01, BR-02, BR-07)
- 할일 등록/목록조회·필터링/수정/삭제 (UC-04~UC-07, BR-03, BR-04, BR-05, BR-06)
- 카테고리 삭제 및 기본 카테고리 이동 (UC-08, BR-08)
- 상태(시작전/진행중/완료/지연) 계산 및 필터 (4장 상태 규칙)
- 반응형 웹 UI (PC/모바일 브라우저 대응)

**Should (여유 있으면 포함)**
- 내 정보 수정 (UC-03)
- 카테고리 생성/이름 수정 (UC-09, BR-09)

**Could (MVP 이후)**
- 정렬 옵션(마감임박순 등), 페이지네이션 UX 고도화
- 다크모드 등 UI 편의 기능

### 3.2 Out of Scope

- 도메인 정의서 7장과 동일: 공유/협업, 알림/리마인더, 반복 일정, 첨부파일/댓글, 소셜 로그인/비밀번호 재설정
- 네이티브 모바일 앱, 접근성(a11y) 대응

## 5. 비기능 요구사항

### 5.1 성능/동시접속 (목표: 1,000명 동시 접속)

- **서버 stateless화**: 인증은 JWT(access_token + refresh_token) 기반으로 처리하여 서버 인스턴스가 세션 상태를 갖지 않도록 한다. 추후 인스턴스 확장 시 로드밸런서만 앞단에 두면 수평 확장 가능한 구조를 확보한다(2일 MVP에서는 단일 인스턴스로 구동하되 구조만 stateless로 유지).
- **DB 커넥션 풀링**: `pg` 라이브러리의 `Pool`을 사용해 커넥션을 재사용한다. 풀 사이즈는 단일 인스턴스 기준 실용적 범위(예: 10~20)로 설정하고, 요청당 커넥션 즉시 반환을 보장한다.
- **인덱스**: 조회 성능 확보를 위해 `todos(user_id)`, `todos(user_id, category_id)`, `todos(user_id, is_completed)`, `categories(user_id)`, `users(email)` unique 인덱스를 적용한다. 상태(시작전/진행중/완료/지연)는 파생값이므로 별도 인덱스 대신 startDate/endDate 조합 조회로 처리한다.
- **N+1 방지**: 목록 조회는 JOIN 또는 단일 쿼리로 처리(카테고리명 등 필요한 정보를 한 번에 조회).
- **페이지네이션**: 할일 목록 API는 페이지/limit 파라미터를 지원해 대량 데이터 조회 시 부하를 제한한다.
- 1,000명 동시접속은 위 실용적 조치(커넥션 풀링, 인덱스, stateless 서버) 수준에서 대응하며, 별도의 캐시 레이어/메시지 큐/멀티 리전 등 과도한 인프라는 2일 MVP 범위에서 도입하지 않는다.

### 5.2 보안

- 비밀번호는 해시(bcrypt 등)로 저장, 평문 저장 금지 (User 엔티티 제약과 동일).
- **인증**: JWT 기반. 로그인 성공 시 access_token(단명, 예: 15분)과 refresh_token(장명, 예: 7일)을 함께 발급한다. access_token은 API 요청 시 `Authorization: Bearer` 헤더로 전달하고, 만료 시 refresh_token으로 재발급 API를 통해 access_token을 갱신한다. refresh_token 만료/무효화 시 재로그인을 요구한다. 미인증 요청은 401로 응답한다.
- 소유권 검증 미통과 시 404 응답으로 리소스 존재 여부 비노출 (BR-05).
- SQL Injection 방지: `pg`의 파라미터 바인딩(`$1, $2...`)만 사용, 문자열 조합 쿼리 금지.

### 5.3 가용성/기타

- 반응형 웹 UI: 모바일/PC 브라우저 뷰포트 대응 (미디어쿼리 또는 반응형 레이아웃), 별도 네이티브 앱 없음.
- 접근성(a11y)은 본 MVP에서 고려하지 않음.

## 6. 기술 아키텍처 개요

기술 스택은 확정된 제약으로 아래를 따른다.

- **프론트엔드**: React 19 + TypeScript. 전역 상태(로그인 사용자 정보, UI 상태 등)는 Zustand로 관리하고, 서버 데이터(할일/카테고리 목록 등)는 TanStack Query로 fetch/캐시/동기화한다.
- **백엔드**: Node.js + JavaScript + Express. `pg` 라이브러리로 PostgreSQL에 직접 SQL 쿼리를 작성한다 (ORM 미사용). REST API로 프론트엔드와 통신. 인증은 JWT(access_token + refresh_token) 기반.
- **데이터베이스**: PostgreSQL 17. User/Category/Todo 3개 테이블, 도메인 정의서 3장의 필드/제약을 스키마에 반영.

레이어 역할: React(뷰/로컬상태) → TanStack Query(서버 상태 캐시, API 호출) → Express REST API(비즈니스 규칙 BR-01~08 검증) → pg Pool(SQL 실행) → PostgreSQL.

## 7. 일정 및 마일스톤 (2일, 1인 개발)

| 일차 | 작업 |
|---|---|
| 1일차 | DB 스키마 설계/생성, 인증(회원가입/로그인) API+화면, 카테고리 자동 생성 로직 |
| 1일차~2일차 | 할일 CRUD API + 화면, 상태 계산 로직, 카테고리/상태 필터 |
| 2일차 | 카테고리 삭제(기본 이동) 처리, 소유권 검증(404) 전수 적용, 반응형 레이아웃 점검, 인덱스/커넥션 풀 설정 확인, 배포 |

Should 항목(내 정보 수정, 카테고리 생성/수정)은 Must 완료 후 잔여 시간에 처리한다.

## 8. 제약 및 가정

- 플랫폼: 웹 우선, 모바일은 반응형 웹으로만 대응(네이티브 앱 없음).
- 기술 스택은 변경 불가한 제약으로 간주(React 19/TS/Zustand/TanStack Query, Node.js/Express/pg, PostgreSQL 17).
- ORM 미사용, SQL 직접 작성.
- 1인 개발/2일 일정으로 인해 Should/Could 항목은 상황에 따라 축소될 수 있다.
- 접근성(a11y)은 이번 범위에서 다루지 않는다.
- 도메인 규칙(BR-01~08), 유스케이스(UC-01~08), 상태 전이 규칙은 도메인 정의서 v0.2를 그대로 준수한다.

## 9. 성공 지표 (KPI)

- MVP Must 요구사항(위 4장) 100% 구현 및 2일 내 배포 완료.
- 할일 목록 조회 API 응답 시간: 정상 부하에서 p95 500ms 이하 (커넥션 풀+인덱스 적용 기준).
- 동시 접속 1,000명 시나리오에서 DB 커넥션 고갈/타임아웃 없이 서비스 유지(부하 테스트로 확인, 정식 성능 테스트는 MVP 이후 별도 진행 가능).
- 소유권 검증 누락으로 인한 타 사용자 데이터 노출 0건.
