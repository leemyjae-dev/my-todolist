# my-todoList 사용자 시나리오

## 버전 이력

| 0.1 | 2026-08-26 | 최초 작성 (PRD v0.2, 도메인 정의서 v0.2 기반) |

## 개요

본 문서는 `2-PRD.md`(v0.2)의 MVP Must 범위 유스케이스(UC-01, UC-02, UC-04~UC-08)와 Should 범위(UC-03)를
사용자 관점의 단계별 흐름으로 구체화한다. 각 시나리오는 `1-domain-definition.md`(v0.2)의 UC/BR ID를 인용해
추적성을 유지한다. 액터는 페르소나 없이 "미가입 사용자", "회원가입한 사용자" 등으로 단순 표기한다.

## 시나리오 1. 회원가입

- **관련 UC/BR**: UC-01, BR-02, BR-07
- **액터**: 미가입 사용자
- **사전조건**: 없음 (서비스 최초 방문)

**기본 흐름**
1. 사용자가 회원가입 화면에서 이메일, 비밀번호(8자 이상), 이름(1~50자)을 입력한다.
2. "가입하기"를 제출한다.
3. 서버는 이메일 중복 여부(BR-07)와 비밀번호 길이를 검증한다.
4. 서버는 비밀번호를 해시하여 저장하고 계정을 생성한다.
5. 서버는 해당 사용자의 '기본' 카테고리(isDefault=true)를 자동 생성한다 (BR-02).
6. 사용자에게 가입 완료를 안내하고 로그인 화면으로 이동시킨다.

**대안/예외 흐름**
- 이메일이 이미 존재: 409 등 오류 반환, "이미 사용 중인 이메일" 메시지 표시 (BR-07).
- 비밀번호 8자 미만, 이름 미입력/50자 초과: 400 오류, 필드별 유효성 메시지 표시.

**사후조건**
- User 레코드와 해당 사용자의 '기본' 카테고리가 생성된다.

## 시나리오 2. 로그인

- **관련 UC/BR**: UC-02, BR-01, BR-07
- **액터**: 회원가입한 사용자
- **사전조건**: 유효한 계정 보유 (시나리오 1 완료)

**기본 흐름**
1. 사용자가 로그인 화면에서 이메일/비밀번호를 입력한다.
2. 서버는 이메일로 사용자를 조회하고 비밀번호 해시를 검증한다 (BR-01, BR-07).
3. 인증 성공 시 access_token(단명)과 refresh_token(장명)을 발급한다.
4. 클라이언트는 토큰을 저장하고 이후 API 요청에 `Authorization: Bearer {access_token}`을 사용한다.
5. 할일 목록 화면(홈)으로 이동한다.

**대안/예외 흐름**
- 이메일 미존재 또는 비밀번호 불일치: 401 오류, "이메일 또는 비밀번호가 올바르지 않습니다" (계정 존재 여부 비노출).
- access_token 만료: refresh_token으로 재발급 API 호출 → 성공 시 계속 진행, refresh_token도 만료/무효면 재로그인 요구.

**사후조건**
- 사용자는 인증된 상태로 자신의 카테고리/할일 리소스에 접근 가능하다.

## 시나리오 3. 내 정보 수정 (Should)

- **관련 UC/BR**: UC-03, BR-05
- **액터**: 로그인한 사용자
- **사전조건**: 로그인 완료(유효한 access_token 보유)

**기본 흐름**
1. 사용자가 내 정보 화면에서 이름 또는 비밀번호를 수정 입력한다.
2. 저장을 제출하면 서버는 본인 계정(access_token의 소유자)만 수정 가능함을 확인한다 (BR-05).
3. 비밀번호 변경 시 재해시하여 저장, updatedAt을 갱신한다.

**대안/예외 흐름**
- 미인증 요청: 401 응답.
- 비밀번호 8자 미만/이름 형식 오류: 400 오류.

**사후조건**
- User 정보가 갱신된다.

## 시나리오 4. 할일 등록

- **관련 UC/BR**: UC-04, BR-03, BR-04, BR-05
- **액터**: 로그인한 사용자
- **사전조건**: 로그인 완료, 최소 '기본' 카테고리 보유

**기본 흐름**
1. 사용자가 "할일 추가" 화면에서 제목(필수), 설명(선택), 시작일/종료일(캘린더 선택), 카테고리(선택)를 입력한다.
2. 카테고리를 지정하지 않으면 서버가 해당 사용자의 '기본' 카테고리를 적용한다 (BR-03).
3. 서버는 startDate <= endDate 를 검증한다 (BR-04).
4. 유효성 통과 시 Todo를 생성한다(isCompleted=false).
5. 목록 화면에 새 할일이 계산된 상태(시작전/진행중/지연 중 하나)와 함께 표시된다.

**대안/예외 흐름**
- 제목 미입력: 400 오류.
- startDate > endDate: 400 오류, "종료일은 시작일 이후여야 합니다" (BR-04).
- 지정한 categoryId가 본인 소유가 아님: 404 (BR-05).

**사후조건**
- 새 Todo가 지정(또는 기본) 카테고리에 생성된다.

---

## 시나리오 5. 할일 목록 조회 및 필터링

- **관련 UC/BR**: UC-05, BR-06
- **액터**: 로그인한 사용자
- **사전조건**: 로그인 완료, 1건 이상의 할일 보유(없어도 빈 목록 정상 조회 가능)

**기본 흐름**
1. 사용자가 할일 목록 화면에 진입한다.
2. 서버는 사용자 소유 Todo만 조회하고, 각 항목의 상태(시작전/진행중/완료/지연)를 서버 UTC 자정 기준으로 계산하여 반환한다 (도메인 정의서 4장).
3. 사용자는 카테고리 필터와 상태 필터를 선택해 목록을 좁혀 조회한다 (BR-06).
4. 목록은 페이지/limit 파라미터로 페이지네이션된다.

**대안/예외 흐름**
- 조건에 맞는 항목 없음: 빈 목록과 안내 문구 표시(오류 아님).
- 미인증 요청: 401 응답.

**사후조건**
- 화면에 필터 조건에 맞는 본인 소유 할일 목록이 표시된다.

---

## 시나리오 6. 할일 수정

- **관련 UC/BR**: UC-06, BR-04, BR-05
- **액터**: 로그인한 사용자(할일 소유자)
- **사전조건**: 로그인 완료, 수정 대상 할일이 본인 소유로 존재

**기본 흐름**
1. 사용자가 목록에서 할일을 선택해 편집 화면으로 이동한다.
2. 제목/카테고리/시작일/종료일/완료 여부 등을 수정한다.
3. 서버는 요청 사용자가 해당 Todo의 소유자인지 검증한다 (BR-05).
4. startDate/endDate 변경 시 startDate <= endDate 를 재검증한다 (BR-04).
5. 완료 여부를 true로 변경하면 completedAt을 기록하고 상태는 즉시 '완료'가 된다.
6. 완료를 다시 false로 되돌리면 completedAt이 초기화되고 날짜 기준으로 상태가 재계산된다.
7. 저장 성공 시 updatedAt이 갱신되고 목록에 반영된다.

**대안/예외 흐름**
- 타 사용자의 할일에 접근: 404 응답, 존재 여부 비노출 (BR-05).
- startDate > endDate로 수정 시도: 400 오류 (BR-04).
- 존재하지 않는 categoryId로 변경: 404.

**사후조건**
- Todo가 수정된 내용으로 갱신되고, 조회 시 최신 상태가 계산되어 표시된다.

## 시나리오 7. 할일 삭제

- **관련 UC/BR**: UC-07, BR-05
- **액터**: 로그인한 사용자(할일 소유자)
- **사전조건**: 로그인 완료, 삭제 대상 할일이 본인 소유로 존재

**기본 흐름**
1. 사용자가 목록 또는 상세 화면에서 삭제를 요청한다.
2. 사용자는 삭제 확인(모달 등)을 진행한다.
3. 서버는 소유권을 검증한 후 (BR-05) 해당 Todo를 삭제한다.
4. 목록에서 해당 항목이 제거된다.

**대안/예외 흐름**
- 타 사용자의 할일 삭제 시도: 404 응답 (BR-05).
- 이미 삭제된 항목 재삭제 시도: 404 응답.

**사후조건**
- 해당 Todo 레코드가 삭제되어 더 이상 조회되지 않는다.

---

## 시나리오 8. 카테고리 삭제 (기본 카테고리로 이동)

- **관련 UC/BR**: UC-08, BR-08, BR-05
- **액터**: 로그인한 사용자(카테고리 소유자)
- **사전조건**: 로그인 완료, 삭제 대상은 isDefault=false인 일반 카테고리이며 본인 소유

**기본 흐름**
1. 사용자가 카테고리 관리 화면에서 일반 카테고리의 삭제를 요청하고 확인한다.
2. 서버는 소유권을 검증하고 해당 카테고리가 '기본' 카테고리(isDefault=true)가 아님을 확인한다 (BR-08).
3. 서버는 해당 카테고리에 속한 모든 Todo의 categoryId를 사용자의 '기본' 카테고리로 일괄 변경한다.
4. 해당 카테고리 레코드를 삭제한다.
5. 목록 화면에서 이동된 할일들이 '기본' 카테고리로 표시된다.

**대안/예외 흐름**
- '기본' 카테고리(isDefault=true) 삭제 시도: 400 오류, "기본 카테고리는 삭제할 수 없습니다" (BR-08).
- 타 사용자의 카테고리 삭제 시도: 404 응답 (BR-05).
- 존재하지 않는 카테고리 삭제 시도: 404 응답.

**사후조건**
- 카테고리가 삭제되고, 소속 Todo는 데이터 손실 없이 '기본' 카테고리로 재배치된다.

---

## 시나리오 9. 카테고리 생성 (Should)

- **관련 UC/BR**: UC-09, BR-09
- **액터**: 로그인한 사용자
- **사전조건**: 로그인 완료

**기본 흐름**
1. 사용자가 카테고리 관리 화면에서 새 카테고리 이름을 입력한다.
2. 서버는 동일 사용자 내 이름 중복 여부를 검증한다 (BR-09).
3. 유효성 통과 시 카테고리(isDefault=false)를 생성한다.
4. 사용자는 이후 할일 등록/수정 시 해당 카테고리를 선택할 수 있다.

**대안/예외 흐름**
- 이름 미입력: 400 오류.
- 동일 사용자 내 동일 이름 카테고리 존재: 409 오류, "이미 존재하는 카테고리 이름입니다" (BR-09).
- 미인증 요청: 401 응답.

**사후조건**
- 사용자 소유의 새 카테고리가 생성되어 목록/필터에 노출된다.
